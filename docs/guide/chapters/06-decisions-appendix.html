What stayed from the prototype, and why

  • Heading-prefixed chunks: still the reason a fact stays attached to its context.
  • The conversation as a transcript in one message for the rewriting step: chat-turn format still makes small models answer instead of analyse.
  • Numbered passages and [n] citations, now validated in code.
  • A fixed refusal sentence and temperature 0: testable refusals and repeatable evaluations.
  • Deciding by measurement: the working method of both guides.
Key idea

The prototype's ideas survived and its code did not. Production is mostly what surrounds the core idea: data variety, filters, routing, safety, monitoring, tests and deployment.

AGlossary of new terms

ADR
Architecture Decision Record: a short document with the context, decision, evidence and consequences of one choice.
Alembic
Versioned database schema migrations for SQLAlchemy.
Bi-encoder
Embeds question and passage separately; compared by vector similarity. Fast, used for search.
Cardinality (metrics)
The number of distinct label combinations; must stay small.
Content hash
A fingerprint of content (SHA-256); equal hash means unchanged.
Cross-encoder
Reads question and passage together and outputs one relevance score. Precise but slow; used for reranking.
DISTINCT ON
Postgres: keep the first row per group, after sorting. Used to pick the version valid today.
Fallback chain
Alternative models tried in order when the primary fails.
GIN index
Postgres index for "which rows contain this word", used for full-text search.
Golden set
Questions with expected routes, sections and facts, used to evaluate every change.
Guardrail
A check before or after the model that blocks, redacts or replaces content.
HNSW
Graph-based approximate nearest-neighbour index; millisecond vector search.
Hit@k / MRR
Share of questions with a relevant passage in the top k / average of 1 ÷ rank of the first relevant passage.
JWT
A signed JSON token; anyone can read it, nobody can alter it without the secret.
LLM-as-judge
A (different) model grading answers against sources and expected facts.
Luhn check
Check-digit formula of payment card numbers.
Matryoshka embedding
An embedding whose prefixes are themselves good, shorter embeddings.
Off-topic gate
Refuse without a model call when no passage reaches a similarity threshold.
One origin
The browser talks to one address; the web server forwards to the API.
OpenTelemetry / OTLP
The open standard (and its protocol) for traces, metrics and logs.
pgvector
Postgres extension adding a vector type, distance operators and vector indexes.
Prompt injection
Text that tries to act as instructions to the model.
Quality gate
A CI check that fails the build if a quality metric drops below a threshold.
Rate limit
A maximum number of requests per client per time window.
Redaction
Replacing personal data with placeholders such as [email].
SSE
Server-Sent Events: a server streams named events to the browser over one HTTP response.
Span / trace
One timed step / the tree of spans for one request.
Structured output
Model output constrained to a JSON schema.
tsvector
Postgres's stemmed-word representation of a text, for full-text search.
Quick tunnel
Cloudflare: a temporary public HTTPS address for a local port, no account needed.

CQuestions you may be asked

How is this different from the prototype?

The core idea is the same: retrieve heading-prefixed passages and answer only from them, with citations. Around it, production added multi-market and multi-language data with versions, one Postgres store with filters in the query, incremental indexing, a routing pipeline with live tools and handoff, guardrails, an API and web app, monitoring, CI quality gates and containers. All of it was measured on a 184-question golden set.

How do you stop the bot from answering a UK customer with German policy?

Retrieval filters by market inside the SQL query, so other markets' passages can never be retrieved. The prompt also names the market, and the golden set has forbidden facts that fail the evaluation if another market's number appears.

How do you handle documents that change on a date?

Versions share a doc_id and have a valid_from. The query keeps, per doc_id, the newest version valid on the query date (DISTINCT ON), so the new version takes over on its date by itself. Re-indexing bumps kb_version, which invalidates the answer cache.

Why not hybrid search, when that is best practice?

It was best in the prototype with a small embedder. With the 4B embedder, every keyword weight lowered Hit@1 (87% dense vs 84% at weight 0.1), and keyword-style questions already reached 92% dense. The hybrid path stays in the code as an option.

How do you know the answers are grounded?

In code: every answer must cite valid passage numbers, or it is replaced by a refusal. In evaluation: an LLM judge from another model family checks that every claim is supported by the cited passages, and 93% were. The remaining 7% are mostly table-row confusion by the 4B model.

What happens with personal data?

It is redacted before it reaches any model, log, trace or database row. The VIN is the only exception, read by code for the recall tool. Answers are scrubbed of anything the customer typed, but not of the company's own contact details.

How would you scale it?

The API is stateless because all state lives in Postgres, so you run more replicas behind one ingress. Move the models to a GPU server or a hosted endpoint, use managed Postgres with pgvector, and let Prometheus scrape every replica (the queries already aggregate with sum). The answer cache cuts repeated questions to about a third of the time.

What would you do next with a budget?

A larger chat model first, because the judge's findings (row confusion, wrong citation numbers) are model limits. Then a multilingual reranker on a GPU for the long public pages, a layout-aware PDF parser, an always-on host, and real customer questions from the feedback export added to the golden set.
