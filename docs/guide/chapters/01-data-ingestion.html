PART A

Data

A retrieval system can only be as good as what it retrieves from, and an evaluation can only prove what its questions test. Part A rebuilds both.

  • 1. From six text files to a knowledge base
  • 2. The golden set: 184 questions that judge every change

1From six text files to a knowledge base

The prototype's knowledge base was six English text files in one custom format, about one brand in one country. Every fact was true everywhere, so nothing could be retrieved "for the wrong customer". Real support content is different. The same company says different things in different countries, documents come as web pages and PDFs, some are in German, and policies change on a date. The production corpus was built to have all of these properties on purpose, so that the system is tested against them.

What the corpus contains

Key idea

A test corpus should contain the difficulties production will have. If every document agrees, a retrieval system that ignores the customer's market looks perfect.

Metadata: the path says most of it

Every file lives at <source_type>/<market>/<language>/<file>, so brand/de/de/warranty.md already says: brand content, German market, German language. A small catalog file holds only what a path cannot say: versions, which car model a document is about, source URLs and licences.

Analogy

A library shelves books by section and language, so the shelf already tells you most things about a book. The index card holds only the extras: the edition and who may copy it.

In this project

data/brand/, data/public/, data/catalog.toml, and the loader ingest/catalog.py. The owner-manual PDFs are rendered from HTML sources by scripts/build_manuals.sh (headless Edge), so they can be rebuilt and diffed.

Pitfall

Public data has licences. GOV.UK content is free to reuse under the Open Government Licence, but only with attribution. The licence and attribution therefore travel with every chunk, and the web app shows them next to a cited source.

2The golden set: 184 questions that judge every change

The prototype had 44 test questions and checked answers for keywords. That was enough to compare a few retrieval modes. It cannot answer production questions such as "does the German customer get the German warranty?" or "does a prompt-injection attempt get through?". The new golden set has 184 questions in 16 categories, and each category exists to catch one specific failure.

CategoryQsWhat it catches
natural60Everyday questions in a customer's own words
german20German questions against German documents
model18Facts about one car model, not another
keyword12Terse queries: "SOS button", "V2L", "LL-26 0W-20"
followup10"And for the Ion X?": needs the conversation
out_of_scope10Must be refused, not invented
market9The same question with a different correct answer per market
cross_lingual · public8 · 8English question, German document · GOV.UK pages
injection · pii6 · 4Attacks; messages containing personal data
tool_recall · tool_charger · handoff5 · 5 · 3Must take the right route, not answer from documents
version · multi_doc3 · 3Today's version wins · facts from two documents

Every question records the route it should take, the relevant sections (for retrieval metrics), the facts a correct answer must contain, and forbidden facts that would prove the wrong market or version was used:

{"id": "uk-001", "category": "natural", "market": "uk", "question": "How long is the warranty on a new car?",
 "route": "kb", "relevant": ["brand/uk/en/warranty#New Vehicle Warranty"],
 "facts": ["3 years", "60,000 miles"], "forbidden": ["50,000 miles", "100.000 km"]}
Key idea

"Forbidden facts" turn a vague worry ("might it mix up markets?") into a test that fails. Here, the US mileage or the German kilometres in a UK answer would fail it.

In this project

backend/eval/golden.jsonl. A unit test (tests/test_corpus.py) checks that every relevant section exists and every expected fact really appears in the documents. Without that test, a typo in the golden set looks like a model error.

Pitfall

Keyword grading needs normalisation. "100.000 km" (German), "100 000 km" and "100,000 km" are the same fact, and some models write numbers with narrow no-break spaces. The grader normalises number formats, Unicode spaces and hyphens, and the golden set allows alternatives such as "15p|15 pence".

If you are asked

"How did you know your changes helped?" — "Every change ran against a golden set of 184 questions in 16 categories, each category targeting one failure: wrong market, wrong version, wrong route, injection, personal data. Answers are graded for required and forbidden facts, and later also by an LLM judge."

Ingestion and storage

How documents in any format become searchable chunks in one database, and why a second run does nothing.

3One converter for every format

The prototype parsed one home-made text format. Production documents are Markdown, HTML and PDF, and more formats will follow. Instead of one chunker per format, every file is first converted to Markdown with Microsoft's open-source markitdown. Everything after that step only has to understand Markdown headings.

.mdused as is
.htmlonly <main> kept; links reduced to their text
.pdftext extracted; headings and lines repaired
→
Markdownone format for the chunker

The two repairs that mattered

  • HTML noise. Converting a whole web page also converts its menu, cookie banner and footer, and those words then match every query. Only the <main> element is converted when the page has one.
  • PDF headings. A PDF stores positioned text, not structure, so "3.1 AC charging" arrives as an ordinary line and the section information is lost. Numbered heading lines are promoted back to Markdown headings, and lines that the page layout wrapped are joined again.
Analogy

A translator who turns every incoming language into English, so the rest of the office only needs to read English.

In this project

ingest/convert.py, decided in ADR 0002.

Pitfall

Tables inside PDFs come out column by column (a limitation of pdfminer, which markitdown uses). Their facts stay in the right section but lose row alignment. Tables in HTML and Markdown are preserved. This is one reason the model sometimes reads a value from the wrong row (chapter 22).

4Chunking by heading, now for any document

The prototype's best idea is kept: one chunk per section, and every chunk starts with its heading path, so "8 years" stays attached to which warranty it describes. What changed is how it works. It now reads Markdown headings at any depth, and long sections are split safely.

Warranty Coverage (United Kingdom) › High-Voltage Battery Warranty (Ion and Vela models)
- Duration: 8 years or 100,000 miles, whichever comes first.
- Northwind guarantees that the battery keeps at least 70% of its original usable capacity …
  • A section longer than 1,200 characters is split on paragraph, then line, then sentence boundaries, with 150 characters of overlap, so a sentence cut in half still appears whole in one piece.
  • Every piece keeps the full heading prefix.
  • A heading with no text of its own (immediately followed by a sub-heading) produces no empty chunk.
backend/src/car_support/ingest/chunk.py (core loop)
for line in markdown.splitlines():
    if m := _HEADING.match(line):
        level, heading = len(m[1]), m[2]
        stack = [(lvl, h) for lvl, h in stack if lvl < level] + [(level, heading)]
        sections.append(((title, *(h for _, h in stack)), []))
    else:
        sections[-1][1].append(line)
Key idea

The heading stack is a small but precise idea. A new heading closes every open heading at its level or deeper, so a "### Claims" heading under "## Battery Warranty" gets the path Title › Battery Warranty › Claims, and the next "## …" heading starts a fresh path.

5One database for everything: Postgres + pgvector

The prototype used two stores: Chroma for vectors, and a BM25 index rebuilt in the app's memory. That breaks in production:

  • Run three copies of the API for load and you have three keyword indexes to keep in sync.
  • Conversations, tickets and feedback need a real transactional database anyway.
  • Filters (market, date) must apply to both searches in the same way.

The answer is one PostgreSQL database with the pgvector extension. Vectors, keyword search, metadata filters and all application data live in one place and can be combined in one SQL query.

Column / tableWhat it does
chunks.embedding vector(1024) + HNSW indexFast approximate nearest-neighbour search by cosine distance
chunks.tsv (generated tsvector) + GIN indexKeyword search, stemmed with the chunk's own language (English or German)
documentsMarket, language, source type, validity date, licence, URL: the filter fields
kb_versionsOne row per index change; part of the answer-cache key
conversations, messages, feedback, tickets, answer_cacheThe product's own data (Part E)

New concept: HNSW

Comparing a question with every stored vector is exact but gets slow as the number of vectors grows. HNSW (Hierarchical Navigable Small World) builds a layered graph in which each vector links to its near neighbours. A search starts at a coarse top layer, jumps towards the question, and refines in the lower layers. It may miss the true best match in rare cases (it is approximate), in exchange for searching in milliseconds. Here a search takes about 11 ms.

Analogy

Finding a street: first the motorway to the right city, then main roads to the district, then side streets. You never drive down every street in the country.

New concept: a generated tsvector

Postgres full-text search stores a tsvector: the text reduced to stemmed words ("charging", "charged" → "charg"). A generated column is computed by the database itself whenever the row changes, so it can never be out of date. Its stemming rules follow the chunk's language, so German compound words and endings are handled properly. BM25 in the prototype treated German text like English.

In this project

db/models.py and the Alembic migrations in backend/alembic/versions/ (0001–0003). Alembic records every schema change as a versioned script, so every environment, from a laptop to CI to a container, reaches the same schema with alembic upgrade head.

If you are asked

"Why not a dedicated vector database?" — "At this size, Postgres with pgvector does dense search, keyword search and metadata filtering in one query, keeps the API stateless, and also stores the app's own data. One system to back up, secure and monitor. A dedicated vector store would make sense at many millions of vectors or for features Postgres lacks."

Pitfall

The vector size is part of the schema (vector(1024)). Changing to an embedding model with a different dimension needs a migration, which is why the bigger embedding model in chapter 8 was asked to produce 1024-dimensional vectors.

6Incremental indexing with content hashes

The prototype rebuilt everything on each run, and its change detection only noticed added or removed sections, not an edit inside one. Production content changes daily, and embedding 408 chunks takes minutes. The new indexer does only the work that is needed.

New concept: a content hash

A hash function (SHA-256 here) turns any text into a short fixed-length fingerprint. The same text always gives the same fingerprint, and changing a single character gives a completely different one. Comparing fingerprints is therefore a cheap, reliable way to ask "has this changed?".

→
Chunk hashmodel + path + chunk text. In a changed file, only new chunk hashes are embedded.
→

Key idea

Put everything that can change the result into the hash: text, metadata, chunk settings and the model. Then "unchanged hash" really means "nothing to do", and you never need a manual "please rebuild" step.

Analogy

A printer who reprints only the pages that changed in a new edition. Every page carries a fingerprint, and a matching fingerprint means the old print is still correct.

In this project

car-support ingest (incremental) and car-support ingest --full. Each run that changes something writes a kb_versions row. The answer cache includes that version in its key, so new content can never be hidden behind an old cached answer.
