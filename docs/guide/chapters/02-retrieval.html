7Filters and versions inside one SQL query

A UK customer must never get the German warranty, and nobody should get the 2027 tariffs in 2026. The prototype had no such problem, since every document applied to everyone. Here, two rules are applied before anything is ranked:

  1. Market: only documents for the customer's market, plus global ones (model guides, manuals).
  2. Version: per doc_id, only the newest version whose valid_from is on or before today.
backend/src/car_support/retrieval/search.py (first step of the query)
WITH eligible AS (
    SELECT DISTINCT ON (doc_id) path FROM documents
    WHERE market IN (:market, 'global') AND valid_from <= :as_of AND source_type = ANY(:source_types)
    ORDER BY doc_id, valid_from DESC
),
dense AS (
    SELECT c.id, row_number() OVER (ORDER BY c.embedding <=> CAST(:qvec AS vector)) AS rank
    FROM chunks c JOIN eligible e ON e.path = c.document_path
    ...

New concept: DISTINCT ON

DISTINCT ON (doc_id) … ORDER BY doc_id, valid_from DESC is a Postgres feature that keeps the first row of each group. Sorted newest first and already limited to dates on or before today, the first row is exactly "the version valid today". When 1 January 2027 arrives, the new tariffs take over by themselves, with no re-index and no deployment.

Filter first, then rank

If you first take the top 4 passages and then drop the wrong-market ones, you may be left with 1 or 0. Filtering inside the query means the 4 results are the best 4 among the allowed documents.

Analogy

Shopping in the UK aisle before comparing prices, instead of picking the four cheapest items in the whole store and then discovering that three are only sold in Germany.

In this project

The Filters(market, as_of, source_types) dataclass in search.py. Because filtering happens inside the query, a passage from another market cannot be retrieved at all; an integration test in tests/test_search.py pins this. The version questions pass 100%, so the 2027 tariff never appears in 2026. The remaining misses in the market category (78% at rank 1) pick the wrong section within the right market, not the wrong market.

Pitfall

as_of comes from the request, not a constant. Tests set it explicitly, so a test written in 2026 does not start failing on 1 January 2027 when the newer tariff document becomes valid.

8A bigger embedding model, and why hybrid search and reranking lost

The prototype's numbers came from 30 chunks. Here there are 408, in two languages, with markets that deliberately contradict each other. Every candidate design was measured on the 146 answerable golden questions.

146 answerable golden questions. Source: ADR 0003 and backend/eval/results/retrieval-*.md.

Lesson 1: the embedding model was the biggest lever

Going from the 0.6B to the 4B Qwen3 embedding model raised Hit@1 by 16 points (71% → 87%). No retrieval trick came close.

New concept: Matryoshka embeddings

The 4B model normally produces 2,560 numbers per text. The schema stores 1,024, and pgvector's HNSW index allows at most 2,000. Qwen3-Embedding is Matryoshka-trained: during training, the first 32, 64, …, 1,024 numbers were each made to work as an embedding on their own. So asking for 1,024 dimensions gives a slightly smaller but still excellent vector, and no migration was needed.

Analogy

Russian nesting dolls: each smaller doll is a complete doll, not a fragment. A JPEG preview is similar, a smaller version of the same picture rather than one corner of it.

Lesson 2: the query instruction is worth 10 points

Qwen3-Embedding was trained with a short task description in front of each question (not in front of the documents). Leaving it out dropped Hit@1 from 87% to 77%.

texts = [f"Instruct: {instruction}\nQuery: {q}" for q in queries]   # llm.py, embed_queries
Pitfall

Read the model card. Many embedding models (Qwen3, E5, BGE) expect a query prefix, and leaving it out is a silent loss. Nothing errors; the results just get worse.

Lesson 3: hybrid search stopped helping

In the prototype, hybrid search was the only mode strong on both natural and keyword questions. With a strong embedding model, every keyword weight lowered the scores. Keyword-style queries such as "SOS button" or "V2L" already reach 92% with dense search alone, so the keyword side mostly added noise. Dense search became the default. The hybrid SQL path stays in the code (CS_RETRIEVAL_MODE=hybrid), because it costs nothing to keep and may matter for exact part numbers in a bigger corpus.

Key idea

A technique that wins with a weak component can lose with a strong one. Hybrid search compensates for weak embeddings, and once the embeddings are strong, the compensation becomes noise. Re-measure when you change a part.

Lesson 4: the reranker was removed

The plan included a cross-encoder reranker, a standard production component. To see why it failed here, compare the two kinds of model:

Bi-encoder (embedding model)Cross-encoder (reranker)
How it readsQuestion and passage separately, each into a vectorQuestion and passage together, as one input
OutputTwo vectors; similarity = their cosineOne relevance score
CostPassages embedded once at ingest; a search takes millisecondsOne model run per (question, passage) pair, at query time
Typical useFind ~30 candidates out of millionsReorder those ~30 precisely

A cross-encoder usually ranks more accurately because it sees both texts at once. Here, the available free CPU rerankers (FlashRank's small ONNX models) were far smaller than the 4B embedding model they were meant to correct:

  • The English cross-encoder added 1 point at Hit@1 over the hybrid candidates it reordered (77% → 78%), still well below dense search alone (87%). It cost about 120 times the search latency (1.3 s instead of 11 ms) and hurt the German questions.
  • The multilingual cross-encoder was harmful (Hit@1 36%), and its scores clustered around 0.999, so they could not serve as a "relevant or not" signal either.

The reranker and the FlashRank dependency were removed.

If you are asked

"Did you use a reranker?" — "I planned one and measured it. With a 4B embedding model, the small CPU cross-encoders added at most one point at over 100 times the latency, hurt German questions, and their scores were too saturated to use as a refusal signal. I removed it, and the decision record keeps the numbers. A larger multilingual reranker on a GPU would be worth testing at scale."

9The off-topic gate, and what a similarity score cannot know

The prototype relied entirely on the prompt to refuse unanswerable questions. Calling the chat model for "what's a good pizza place?" is wasted time and money, so production adds a cheap gate. If not a single retrieved passage reaches a minimum cosine similarity, the assistant refuses without calling the chat model.

Choosing the threshold from data

  • With the 4B model, the lowest similarity of any answerable question was 0.448 (a bare keyword query, "LL-26 0W-20").
  • The threshold was set just below that, at 0.40, so the gate wrongly refuses none of the answerable questions.
  • It catches only the obviously unrelated questions: 2 of 10 out-of-scope ones (pizza, football).

Why it cannot do more

"What is the Ion 4's drag coefficient?" is about the right car, uses the right vocabulary, and scores 0.69, which is higher than many answerable questions. But the documents simply do not contain the number. No similarity score can tell "on-topic and answered" from "on-topic but not answered", because similarity measures topic, not whether the answer is present. That decision belongs to the grounded answer step, which refuses when the passages lack the fact (chapter 14).

Key idea

The gate is a cheap filter for the obvious cases, not a judge of answerability. Two layers do two different jobs.

The threshold depends on the model

When CI ran retrieval with the smaller 0.6B model (to fit on a free CI machine), the 0.40 threshold wrongly refused 3 answerable questions. The smaller model's similarities simply run lower: its lowest answerable question scores 0.303. The threshold is therefore stored per model, each value measured on the golden set:

RELEVANCE_THRESHOLDS = {"qwen3-embedding:4b": 0.40, "qwen3-embedding:0.6b": 0.28}   # config.py
# An unmeasured model gets no gate; the grounded answer step still refuses.
Pitfall

Similarity thresholds are not portable between embedding models (or even model versions). Treat a threshold as a measured property of a specific model, and re-measure it whenever the model changes.

10Speed on a laptop: two surprising fixes

Two changes with nothing to do with AI mattered more for speed than any model choice.

Fix 1: 127.0.0.1 instead of localhost

Embedding one question took 2.3 seconds. The model was not the problem. On Windows, localhost resolves to the IPv6 address first, the local server was listening on IPv4, and every new connection waited about 2 seconds before falling back. Writing the IPv4 address directly brought a query embedding down to 74 ms, about 30 times faster.

Analogy

Ringing the front door of a house whose owner only ever answers the side door. They do answer eventually, after you give up on the front door.

Fix 2: question embeddings on the CPU

The laptop GPU has 6 GB of memory. The 4B embedding model (~3.4 GB) and the 4B chat model (~3.4 GB) do not fit together, so Ollama unloaded one to load the other, for every question: 5–10 seconds of swapping. Embedding a single short question is light work, so it now runs on the CPU (about 0.5 s) while the chat model stays resident on the GPU. A knowledge-base answer now takes 1.6–2.8 s.

"options": {"num_gpu": 0} if on_cpu else {}     # llm.py: zero GPU layers = run on the CPU
Key idea

Measure where the time goes before optimising. Here the big wins were a network detail and memory placement, not a smaller model.

In this project

CS_OLLAMA_URL=http://127.0.0.1:11434, CS_QUERY_EMBEDDING_ON_CPU=true. Document embeddings at ingest still use the GPU, where batch throughput matters.

Pitfall

The full local stack (Postgres, the 4B embedder, the 4B chat model, a browser, the IDE) needs about 16 GB of RAM. When memory ran out, the local model runner crashed in the middle of an evaluation. That led to the retry-and-degrade design in chapter 15. Lighter options are the 0.6B embedder or a cloud chat model.
