The pipeline

11The new graph: guard, understand, route

Customers do not only ask questions the documents answer. They ask "is there a recall on my car?" (live data), "where can I charge near Munich?" (live data), "let me talk to a person" (handoff), or "who won the match?" (off-topic). Some send attacks. The graph now routes each message to the right destination.

guard ─┬─ injection ─► blocked
       └─ understand ─┬─ question ───────► cache ─┬─ hit ─► cached answer
                      │                           └─ miss ─► retrieve ─┬─ relevant ─► generate ─► validate ─► store
                      │                                                └─ off-topic ─► refuse
                      ├─ recall_lookup ──► recall (NHTSA)
                      ├─ charger_search ─► chargers (OpenStreetMap + Open Charge Map)
                      ├─ human_agent ────► handoff (ticket)
                      └─ off_topic ──────► off_topic

Why one "understand" call instead of condense + router

The usual design has two model calls: one rewrites follow-ups into standalone questions (the prototype's condense step), and one router picks the path. Each call to a 4B model costs about a second. Both need the same input, the conversation and the latest message, so one structured call returns everything at once:

backend/src/car_support/pipeline/prompts.py
class Understanding(BaseModel):
    intent: Intent                     # question, recall_lookup, charger_search, human_agent, off_topic
    standalone_question: str           # follow-ups resolved from the transcript
    vin: str | None = Field(description="17-character vehicle identification number, if given")
    make: str | None                   # for a recall lookup without a VIN
    model: str | None
    year: int | None
    location: str | None               # for a charger search

New concept: structured output with an enforced schema

Asking a model "reply in JSON" is a request it can ignore. With schema-enforced structured output, the model server (Ollama, or Groq) restricts generation so that only tokens that keep the output valid against the JSON schema can be produced. The result always parses into the Pydantic class, with no fragile text parsing.

Analogy

A paper form with labelled boxes instead of a blank sheet. The person filling it in can still write something wrong in a box, but cannot forget that the box exists or invent a new one.

Key idea

Only two nodes call a chat model: understand and generate. Everything else is plain code, which is fast, testable and predictable.

In this project

pipeline/graph.py builds the graph with LangGraph's StateGraph. Every node is wrapped by timed(name), which records its latency for the dashboard (chapter 21). The conversation is still passed as a transcript inside one message, not as chat turns, which was a measured lesson from the prototype.

12Deterministic guards around a small model

The first version of the pipeline let the model decide everything. The evaluation showed exactly where a 4B model fails, and each failure was fixed by moving that decision into code:

Observed failure (gemma3:4b)Fix in codeEffect
Optional tool fields were left out of the JSON, so recall lookups asked for a VIN the customer had already givenFields made required but nullable (str | None with no default): the model must write each one, even if only as nullRecall routing 20% → 100%
Asked to report the language, the model labelled English questions German after seeing a German exampleLanguage detected by a word-list heuristic, not the modelGerman category 95%
VINs copied with a character missing or changedA VIN must match the 17-character VIN pattern; otherwise it is read from the message with a regexNo invented VINs
"Is there a recall?" with no car named sent to the recall toolA tool without its arguments becomes a normal question; the documents explain how recalls workNo pointless "please give details" replies
The structured call failed (model down, invalid output)Rules take over: a VIN means recall, "human/agent" means handoff, otherwise a questionNever an error page
backend/src/car_support/pipeline/graph.py
def _check_tool_arguments(u: Understanding, question: str) -> Understanding:
    vin = u.vin if u.vin and _VIN.fullmatch(u.vin.upper()) else None
    if not vin and (found := _VIN.search(question.upper())):
        vin = found[0]  # a VIN is unambiguous: do not rely on the model to copy it
    u = u.model_copy(update={"vin": vin})
    vehicle_known = bool(vin or (u.make and u.model and u.year))
    if (u.intent == "recall_lookup" and not vehicle_known) or (
        u.intent == "charger_search" and not u.location
    ):
        return u.model_copy(update={"intent": "question"})
    return u

Together these fixes raised the pipeline from 91% routed / 83% correct to 95% routed / 86% correct, with tool routing going from 20–40% to 100%.

Key idea

Let the model do what only a model can (understanding free text, resolving "and for the Ion X?"). Let code do what code does perfectly (pattern matching, checking, defaults). A small model plus deterministic guards beats a small model alone.

Analogy

A new employee takes the customer's call, while a checklist on the desk catches the typical slips: did you write the VIN down correctly? Did you get an address before booking a technician?

Pitfall

"Optional" fields in a schema are an invitation for a small model to skip them. If your code needs a field to be considered, make it required and allow null.

If you are asked

"How do you make a small model reliable?" — "Measure where it fails, then take those decisions away from it. In this project, the language detection, VIN extraction and tool-argument checks moved into code. Tool routing went from 20–40% to 100%, and the model is left with the parts that need language understanding."

13Live tools: recalls and chargers from open data

Some answers cannot come from documents, because they change daily or depend on the customer's car or location. Two free public services cover them.

ToolServices (free)What happens
Recall checkNHTSA vPIC (decodes a VIN into make, model and year) and NHTSA Recalls; US government, public domain, no keyVIN → vehicle → list of recall campaigns with component and summary. Outside the US, a note says that NHTSA covers US vehicles.
Charger searchOpenStreetMap Nominatim (place name → coordinates) and Open Charge Map (chargers near coordinates); free key, CC BY 4.0Up to 5 public chargers within 5 km, with distance, power and connectors, and the data licence shown

Three rules for calling someone else's free service

  1. Short timeouts (10 s). A slow external service must not hang the chat.
  2. Cache results. Recall data changes slowly, and Nominatim's usage policy allows at most one request per second, so repeated questions are answered from memory.
  3. Fail into a helpful reply. Every failure becomes a ToolUnavailableError, and the customer gets "that service is not available right now; shall I connect you with a colleague?" instead of an error.

Tool replies are built from fixed templates, not by a model. Live data is shown exactly as received, with its source, and no model can misquote a recall campaign number.

In this project

pipeline/tools.py (calls, caching, an identifying User-Agent, as Nominatim requires) and the recall/chargers nodes in graph.py. The tool_recall and tool_charger golden categories reach 100% routing.

Pitfall

Charger search needs a free Open Charge Map API key. Without one, the tool reports "unavailable" and offers a person. That is the designed degradation, not a crash. A recall result describes the model year; whether a particular car was already repaired can only be confirmed by a dealer, and the reply says so.

14Grounded generation and validation

The answer prompt keeps the prototype's rules (numbered passages, cite every fact, a fixed refusal sentence, temperature 0) and adds what production needs:

  • The customer's market: "where passages differ by market, answer for that market".
  • The customer's language: "reply in German, even if the passages are in English". Cross-lingual questions reach 100% routing.
  • Partial answers: answer the parts the passages cover and say which part is missing.
  • Passages are data: they sit between <passages> tags and are declared reference text, not instructions (chapter 20).

The validate step: trust, but verify

The model's answer is never shown as is. A deterministic validate node checks it first:

Normalise【1】 → [1], [1-4] → [1, 2, 3, 4], odd spaces and hyphens
→
Refusal or leak?→ the fixed refusal
→
Drop invalid citations[7] with 4 passages is removed
→
No citation left?→ refusal: no uncited claims
→
Scrub echocustomer's personal data removed

Only the cited passages become the "sources" shown under the answer, with title, section, licence and the passage text.

Pitfall

Models differ in how they write citations. The cloud model gpt-oss writes 【1】 (CJK brackets) and puts narrow no-break spaces inside phone numbers. Before normalisation, valid answers were being thrown away as "uncited". Test the validator with every model you allow.

Key idea

An answer that cites nothing is treated as a failed answer, not a confident one. This rule turns "the model invented something" from an invisible error into a visible refusal plus an offer to talk to a person.

15Models: local first, free cloud optional, never crash

A model is chosen with one setting, CS_CHAT_MODEL, written as provider:model. LangChain's init_chat_model turns that string into a client, so switching from the local model to a cloud model is a configuration change, not a code change.

Resilience: retry, fall back, degrade

def _resilient(primary, fallbacks):
    model = primary.with_retry(stop_after_attempt=2)  # a crashed local runner restarts on retry
    if not fallbacks:
        return model
    return model.with_fallbacks([f.with_retry(stop_after_attempt=2) for f in fallbacks])
  1. Retry once. When the local Ollama runner crashed under memory pressure, the next request restarted it, so one retry turned a crash into a delay.
  2. Fallback chain. CS_FALLBACK_CHAT_MODEL takes a comma-separated list of models, tried in order.
  3. Degrade. If every model fails, the customer reads "service unavailable, shall I connect you with a colleague?", and the failure is counted on the dashboard.

New concept: free-tier quotas

Groq's free tier allows 200,000 tokens per model per day. One full evaluation run uses about 220,000, so cloud evaluations run in two halves (--part 1/2, then --part 2/2) on different nights. A fallback chain over different models multiplies the daily capacity, because each model has its own quota.

Pitfall

Models get retired. The originally planned Groq model (llama-3.3-70b) was no longer offered when the pipeline was built, which is why the model is a setting, not a constant. And spreading load over several free accounts to get around limits breaks the provider's terms, so the project uses one key.

If you are asked

"What happens if the LLM is down?" — "Each call retries once, then walks a configurable fallback chain. If everything fails, the customer gets a polite 'unavailable, shall I connect you with someone?' and a counter goes up on the dashboard. The understand step falls back to rules, and tools fail into the same reply. The chat never shows an error."
