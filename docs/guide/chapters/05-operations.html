21Observability: metrics, dashboards and traces

Running an assistant means answering three kinds of question, and each needs a different tool:

QuestionToolIn this project
Is it healthy right now? Getting better or worse?Metrics: numbers over timePrometheus + a Grafana dashboard
Why was this answer bad?Traces: one request, step by stepOpenTelemetry → Arize Phoenix
What happened at 10:42 for request X?Logs: events with contextJSON lines with the request ID

New concept: Prometheus metrics

The API keeps counters and histograms in memory, such as "answers by outcome and market", "seconds per pipeline step", "cache hits", "ratings", "handoffs by reason", "tool failures", "model failures after retries" and "blocked injection attempts". It exposes them as text at /metrics. Prometheus fetches ("scrapes") that page every 15 seconds and stores the time series, and Grafana draws them.

cs_answers_total{outcome="answer",market="uk"} 128
cs_answers_total{outcome="refuse",market="uk"} 9
cs_step_seconds_bucket{step="generate",le="2.5"} 117

Illustrative values; the metric names are the real ones from observability.py.

Key idea

Labels must have small, fixed value sets (outcome, market, step). A label such as "question text" or "user ID" creates a new time series per value and can take the monitoring system down. That problem is called cardinality explosion.

New concept: a trace and spans

A trace is the story of one request. It is made of spans, one per step, each with a start, a duration and attributes. The OpenInference instrumentation for LangChain records every graph node, prompt, model call and retrieval as spans automatically, and FastAPI's built-in telemetry adds the HTTP span around them, so one customer message is one trace. In Phoenix you click a bad answer and see what the question was rewritten to, which passages came back with which scores, the exact prompt, and how long each step took.

Analogy

Metrics are the dashboard of a car (speed, temperature, fuel). A trace is the black-box recording of one particular journey. You watch the dashboard all the time, and you replay the recording when something went wrong.

Keeping personal data out of observability

Traces record prompts, so a trace store can quietly become a database of customers' personal data. Here the question is redacted before the graph starts (chapter 20), so traces only ever see [email] or [phone]. FastAPI's telemetry "logs", which would include raw request bodies on validation errors, are switched off, and health checks and /metrics produce no spans.

  • A message containing an email address and a phone number left no trace of either in 172 stored spans.
  • After a mixed run, the counters reconciled exactly: 7 messages reached the guard, 6 the understand step (one was blocked), 5 the cache (one went to the recall tool), 4 retrieval (one was a cache hit).
In this project

observability.py (metrics, the timed decorator, tracing set-up); infra/prometheus.yml; infra/grafana/, where the dashboard is generated by build_dashboard.py and provisioned automatically, with a colour-blind-validated palette and red reserved for "unavailable". Start everything with docker compose --profile observability up -d: Phoenix on :6006, Prometheus on :9090, Grafana on :3001.

Pitfall

Right after an API restart, Prometheus increase() undercounts in short time ranges, because a new counter's first value is never seen as an increase. Use longer ranges for reports. And Phoenix is source-available (Elastic License 2.0), free to self-host but not OSI open source; since the app only speaks OTLP, any OpenTelemetry backend such as Jaeger can replace it.

22Evaluation and CI: from keyword checks to an LLM judge

Three levels of evaluation

LevelMeasuresCostWhen
RetrievalHit@1, Hit@4, MRR per categoryEmbeddings only, ~1 minEvery pull request (CI gate)

New concept: LLM-as-judge

Keyword checks are cheap and repeatable but blind to one thing that matters most: an answer can contain the right fact and still not be supported by the passage it cites. A judge model reads the question, the answer and the cited passages, and returns a structured verdict (faithful, correct, reason). Two rules make it trustworthy:

  • A different model family from the one being judged (Qwen judging Gemma), so the judge does not share its blind spots.
  • Calibrated before use: three hand-made answers with known verdicts (correct and grounded; a true-sounding but unsupported fact; a wrong number). The judge graded all three correctly.
RoutedCorrect (keywords)Cites relevantJudge: faithfulJudge: correct
gemma3:4b, all guardrails on96%86%88%93%87%

184 golden questions; 146 answered knowledge-base questions judged by qwen/qwen3.8-27b on Groq.

The judge's correctness (87%) agrees with the keyword grader (86%), which cross-validates both. What the judge adds is faithfulness, and its findings show two patterns: row confusion (the Ion 4's towing limit given for the Ion X; the Aero's £899 service-plan price given for the Ion, which costs £699) and the right fact with the wrong citation number. Both are limits of a 4B model reading tables, and they are the main argument for a larger chat model in production.

Key idea

Cheap deterministic checks first, a judge on top. When the two agree on correctness, you can trust both, and the judge's extra signal (faithfulness) tells you which kind of error remains.

CI: what runs on every pull request

JobChecks
backendruff format and lint, mypy (strict), 252 pytest tests, including integration tests against a real Postgres in a throwaway container (testcontainers)
frontendESLint, TypeScript, production build, Playwright tests of the real UI against a mocked API
retrieval-gateReal corpus, real embeddings (Ollama with the 0.6B model, which fits a free CI machine), real Postgres: the build fails if Hit@4 < 0.88 or MRR < 0.76. CI measured 92% / 0.818, the same as on the laptop.
securitypip-audit (Python dependencies), npm audit (JavaScript), Trivy filesystem scan
imagesBoth Docker images built and scanned with Trivy

Nightly: the full pipeline on Groq's free tier with the judge, half the golden set per night (alternating), because one full run (~220,000 tokens) exceeds the daily quota. Dependabot proposes dependency updates weekly, and each one has to pass the same gates.

New concept: a quality gate

Unit tests check that code does what it says. A quality gate checks that the system is still good enough: here, that retrieval did not get worse. A change to chunking, the SQL, a prompt prefix or a dependency that silently lowers retrieval quality fails the build, just as a broken test would.

Pitfall

The gate found a real bug on its first run. The off-topic threshold of 0.40, tuned for the 4B model, wrongly refused 3 answerable questions with CI's 0.6B model. Thresholds became per-model values (chapter 9). Running the evaluation in a second environment is how such hidden assumptions surface.

If you are asked

"How do you evaluate a RAG system in CI?" — "In three layers. On every pull request, a retrieval gate indexes the real corpus and fails below Hit@4 0.88 or MRR 0.76. Nightly, the full pipeline runs against 184 golden questions with deterministic fact checks, plus an LLM judge from a different model family for faithfulness. The judge was calibrated on known cases, and its correctness agrees with the keyword grader within one point."

23Deployment: containers, one origin, a free public link

Containers

A container image packages the application with exactly the runtime and libraries it needs, so "works on my machine" becomes "works on every machine". Both images follow the usual production rules:

  • Multi-stage builds: dependencies are installed in a build stage, and only the result is copied into a slim final image. The API image is 862 MB (Python, ML clients, the knowledge base) and the web image 386 MB (Next.js standalone output).
  • Non-root user (uid 1000), so a compromised process cannot modify the image.
  • Pinned versions of base images and tools, so builds are reproducible.
  • The API runs its database migrations on start-up, so a new version brings its own schema.

Compose profiles: one file, several stacks

docker compose up -d                            # Postgres only (development)
docker compose --profile app up -d --build      # + API (:8000) and web app (:3000)
docker compose --profile observability up -d    # + Phoenix, Prometheus, Grafana
docker compose --profile ollama up -d           # + Ollama in a container (default: host, for the GPU)

One origin

The browser talks only to the web app. Customer calls go to /backend/v1/…, which the Next.js server forwards to the API, and agent calls go through the signed-in /api/agent/… route (chapter 18). The forwarder allows only the four customer routes and passes the client's address on, so rate limits stay per customer. One origin means no CORS configuration and one address to publish.

frontend/src/app/backend/[...path]/route.ts
const ALLOWED = new Set(["chat", "feedback", "handoff", "conversations"]);

Pitfall

Behind a proxy, every request seems to come from the proxy, so one rate limit would apply to all customers together. The API reads the real client address from X-Forwarded-For, but only when the request comes from a trusted proxy (CS_FORWARDED_ALLOW_IPS). Otherwise any client could fake the header and dodge its limit.

The free public demo: when the plan met the price list

The plan was a frontend on Vercel, the API on a Hugging Face Docker Space, Postgres on Neon and the model on Groq, all free. The zero-cost rule required re-checking every free tier before use, and the re-check changed the plan:

ServiceFinding (October 2026)
Hugging Face Docker SpacesNow require a paid plan to create; only static Spaces are free
Render free tier512 MB RAM, far too little for the embedding model; card verification reported
Fly.io, Railway, cloud free tiersNeed a credit card
Neon, Vercel HobbyStill free, but useless without a free API host

The replacement needs no account at all: a Cloudflare quick tunnel. One command, cloudflared tunnel --url http://localhost:3000, gives the running local stack a public https://….trycloudflare.com address. Thanks to the single origin, one tunnel is enough. The end-to-end test through the tunnel worked: chat, streaming, citations and handoff.

Key idea

A rule such as "re-check free terms before use; drop anything that needs payment" only has value if you follow it when it hurts. The plan changed, and the reason went into a decision record (ADR 0007).

Pitfall

The tunnel is online only while the laptop runs it, its address changes on every start, and it carries no uptime guarantee. A stable address needs a domain, which costs money. Never leave a public tunnel running unattended: it exposes the machine's chat to anyone with the link.

If you are asked

"How would you deploy this for real?" — "The images are ready for any container host. Put the API and web containers behind one ingress, use a managed Postgres with pgvector, keep the model behind CS_CHAT_MODEL, scale the stateless API horizontally, and have Prometheus scrape each replica. The demo uses a quick tunnel only because no free, card-less host fits the API."
